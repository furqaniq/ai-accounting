Architecture

One browser, one API, one system of record, with queue and object storage isolated on Render.

Live topology
01BrowserNext.js app on the Vercel edge
02Vercel frontendRoot directory frontend; production alias
03Render APINestJS Docker service; /api/v1
04Neon PostgresSystem of record; migrations + seed
05KV + MinIOBullMQ queue and attachment objects

Request path

The browser loads the static Next.js app from Vercel. Client-side API calls go to https://daybook-api-9nwb.onrender.com/api/v1 with a Bearer token and X-Organization-Id. Render terminates TLS and forwards to the NestJS container on its injected port. Prisma reads and writes Neon over TLS.

CORS is pinned to https://daybook-ai-accounting.vercel.app; credentials are not used by the app, but the API enables CORS credentials consistently with the NestJS configuration.

Side paths

Agent jobs are queued in Render Key Value and consumed by the in-process BullMQ worker in the API service. Attachments go to MinIO over HTTPS; the API stores metadata in Postgres and returns 15-minute presigned GET URLs from the public MinIO host.

MinIO sits on the public network because the free Render private hostname did not resolve from the API container. The backend therefore uses the public endpoint for both the SDK and presigning.

Provisioning sequence

The order used, including the checks that prevented a broken first connection.

Completed
  1. Create the Neon project
    Project ai-accounting, Postgres 16, database daybook, role daybook_owner, region aws-ap-southeast-1. Retrieve the direct TLS connection URI; do not use the pooled URI for migrations.
  2. Create Render Key Value
    Free instance daybook-redis in Singapore, maxmemory policy noeviction. Render services use the internal URL; no external access is enabled.
  3. Create the MinIO web service
    Image docker.io/bitnamilegacy/minio:latest, command minio server /bitnami/minio/data --address :10000, health check /minio/health/live. The first /data command failed with file access denied; the writable Bitnami data path fixed it.
  4. Create the Render API
    Docker web service from furqaniq/ai-accounting, branch main, root backend, health check /api/v1/health, free plan. Docker CMD runs prisma migrate deploy before Nest starts.
  5. Set secrets and connect services
    Add Neon, Redis, JWT, CORS, MinIO, and agent variables in Render. MinIO initially used the private hostname; DNS failed with ENOTFOUND daybook-minio, so both SDK and presigning use the public HTTPS endpoint.
  6. Migrate and seed
    Run Prisma against Neon, then run the deterministic seed with AGENT_QUEUE_DRIVER=inline. All migrations applied and both organizations seeded successfully.
  7. Create the Vercel project and deploy
    Project daybook-ai-accounting, root frontend, framework Next.js; add NEXT_PUBLIC_API_URL before building; production deployment READY on the alias. The old ai-accounting-beta.vercel.app domain 308-redirects to the new name.

Normal deploy

  • Backend: push to main; Render builds backend/ on the Dockerfile and runs migrations at start.
  • Frontend: push to main; Vercel builds the frontend root automatically. The old domain redirects permanently to the new one.
  • Docs: static root HTML changes do not require a runtime deploy.

Database changes

  • Add migrations in chronological filename order.
  • Run prisma migrate deploy against Neon before relying on new code.
  • Reseed only when demo fixtures change; the seed is idempotent.

Logs

  • Render Dashboard → daybook-api → Logs for Nest/Prisma/BullMQ.
  • MinIO logs show startup and object errors.
  • Vercel → Deployments → Build Logs for Next.js failures.

Rollback

  • Vercel: promote a previous READY production deployment.
  • Render: roll back to the previous live deploy.
  • Neon: restore a branch or point-in-time snapshot; migrations are forward-only.

Operations

The demo works now; these are the tasks that keep it trustworthy.

Runbook

Backups and recovery

Neon is the system of record. Use Neon branches and point-in-time restore before destructive changes. Attachments are not backed up: the free MinIO service has no persistent disk, so objects disappear on a restart or redeploy. Add a Render disk or move objects to durable S3-compatible storage before storing real receipts.

Queue recovery

Render Key Value free has no persistence. In-flight jobs can be lost on restart. Cron definitions live in Postgres and the backend re-registers enabled rows at startup; historical agent logs and jobs are in Postgres and survive.

Secret rotation

Rotate JWT_SECRET to invalidate sessions; rotate the MinIO pair in both MinIO and the API together; rotate the Neon role password and update DATABASE_URL. Never add real credentials to this document or the repository.

Monitoring

Use Render health checks for the API and MinIO, Vercel deployment status for the frontend, and Neon metrics for compute/storage. The API has no external uptime monitor or alert routing yet.
