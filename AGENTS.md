## Implemented architecture (001–025)
### Backend
- API prefix `/api/v1`; global `ValidationPipe` with `whitelist`, `forbidNonWhitelisted`, `transform`; CORS from `CORS_ORIGINS`, exposing `Content-Disposition`.
- Auth: `POST /auth/login`, `/auth/refresh`, `/auth/logout`, `GET /auth/me`; JWT access tokens plus hashed, rotating refresh tokens. Every tenant request sends `Authorization: Bearer <token>` and `X-Organization-Id`.
- Modules: `auth`, `tenant`, `accounts`, `ledger`, `sales` (customers, items, invoices, estimates, PDFs, payments, AR aging), `purchases` (vendors, bills, bill payments, quick expenses, AP aging), `attachments` (the MinIO-backed `AttachmentStore`), `banking` (bank accounts, imports, transactions, categorization rules, matching, transaction resolution, reconciliation sessions), `projects` (projects, time entries, invoice roll-down, project profitability), `reports` (`ReportingEngine` plus P&L, balance sheet, cash flow, trial balance, and operational analysis endpoints), `events` (`DomainEventsService`), and `agent` (`ToolRegistry`, `AgentPolicyService`, `AiProviderService`, orchestrator, BullMQ prompt worker, automation scheduler/worker/runner, domain-event router, prompt/job/log/policy/automation endpoints).
- `TenantContextService` is a singleton backed by `AsyncLocalStorage`: a global middleware puts each HTTP request in context (guards still populate `request.user`/`request.tenantMembership` lazily), and `runAs({user, membership}, fn)` does the same for BullMQ workers after re-resolving membership from the DB. `ScopedDataAccess`, `AuditService`, and `LedgerService` are therefore singletons, not REQUEST-scoped. `ScopedDataAccess` is the default tenant boundary: add every new organization-owned model to its `ScopedModel` union and query through it. Direct Prisma calls are for transactional/locking paths only, must still filter `organizationId`, and must never trust a caller-supplied org id.
- `permissions.ts` is the single role → permission matrix. Permission names follow `${domain}:read|manage`; current domains include org, members, audit, accounts, ledger, customers, items, invoices, estimates, payments, vendors, bills, expenses, attachments, banking, projects, time, agent, plus `reports:read` (granted to every role). `agent:approve` and `agent:policy` are granted only to Owner/Admin; Staff/Accountant hold `agent:read` + `agent:manage` (automation CRUD and the `automation.create` tool), Viewer keeps `agent:read` only, and Staff/Accountant can propose writes when they hold the tool's business permission. `agent:policy` governs the per-organization auto-execute/approval overrides without broadening `agent:manage`. Endpoints declare `@RequirePermission`; Owner/Admin/Accountant/Staff manage business records, Viewer is read-only.
- Audit every user state change through `AuditService` (`AuditLogEntry`). Agent activity is separate and append-only in `AgentActionLog`; neither log has update/delete paths. Action names must match `^[a-z]+(\.[a-z_]+)+$` (for example `bill.pay`); hyphens are rejected.
- `LedgerEngine` is the only journal writer. Use `postWithin(tx, ...)` when a feature transaction needs an atomic post, otherwise `postEntry`. Journal references are per-org `JE-####`; posted entries are immutable and corrected by reversal. The unique key `(organizationId, sourceType, sourceId)` makes feature postings idempotent.
- `BankingImportEngine` is the only bank-file parser, mapper, and normalizer; the UI never parses files. It returns preview rows and duplicate fingerprints, and the banking import service persists a batch plus normalized transactions atomically.

### Domain rules
- Sales: `CUST-####`, `ITEM-####`, `INV-####`, `EST-####`, `PAY-####` are per-org. Invoice drafts are editable; sending posts AR `1100`, income accounts, and sales tax `2100` once. DB invoice statuses are DRAFT/SENT/PARTIAL/PAID; OVERDUE is derived from `dueDate`.
- Estimates convert only when ACCEPTED, create a DRAFT invoice, and store a unique `convertedInvoiceId`; no ledger post until that invoice is sent.
- Invoice PDFs: `GET /invoices/:id/pdf`, `application/pdf`, `INV-####.pdf`; `pdfkit` runtime, `pdf2json` dev-only for text assertions.
- Customer payments: `PAY-####`; one RECEIVED receipt applies across one or more open invoices for one active customer, and the receipt total must equal the applied sum. Row-lock invoice reads; reject over-application. Partial sets PARTIAL, full sets PAID/`paidAt`, and the payment posts Cash `1000` debit / AR `1100` credit once. Payments are create-only; no unapplied credit or reversal yet.
- AR aging: `GET /reports/ar-aging?asOf=YYYY-MM-DD`; buckets current/1–30/31–60/61–90/90+. As-of uses invoice `issueDate` and payment `date` (not `sentAt`/`paidAt`); drafts excluded; `current` includes due today; `1–30` starts one day past due. Totals must reconcile to open invoices.
- Purchases: `VEND-####`, `BILL-####`. Bill lines must use active EXPENSE accounts; tax uses the org default or an explicit rate and posts to purchase tax receivable `1300`. Opening validates active AP `2000` (and `1300` when taxed), row-locks the bill, posts expense debits + tax debit + AP credit once, and sets OPEN. Only DRAFT bills are editable; DB statuses are DRAFT/OPEN/PARTIAL/PAID and OVERDUE is derived. Vendor balance = non-draft bills `total - amountPaid`.
- Bill payments: `BPAY-####`; one SENT payment applies across one or more OPEN/PARTIAL bills for one active vendor, and the payment total must equal the applied sum. Row-lock bill reads; reject drafts, paid bills, mixed vendors, over-application, and mismatched receipts. Partial sets PARTIAL, full sets PAID/`paidAt`, and the payment posts AP `2000` debit / Cash `1000` credit once. Bill payments are create-only; no unapplied credit or reversal yet.
- AP aging: `GET /reports/ap-aging?asOf=YYYY-MM-DD`; same five buckets. As-of uses bill `issueDate` less `BillPaymentApplication` amounts whose payment `date` is on or before the as-of date; drafts and later payments excluded; totals must reconcile to open bills. `reports:read` covers it.
- Quick expenses: `EXP-####`; required active EXPENSE category, optional active vendor, date, two-decimal amount, memo, and optional receipt note. Creating posts category debit / Cash `1000` credit once through `LedgerEngine`. Financial edits reverse the prior entry and post a corrected `:vN` entry; memo/vendor-only edits stay off the ledger. List filters by date range, category, vendor, and search; Viewer read-only.
- Banking rules: `CategorizationRule` stores `descriptionContains`, an active target ledger account, a priority, and an active pause switch. Matching is case-insensitive and whitespace-normalized; lower priority wins, then the older rule, then id, and every transaction uses at most one rule. Rules apply at import time, set `categoryAccountId`/`categoryRuleId` and `CATEGORIZED`, and post one `BANK` journal per transaction (inflow debits the bank and credits the target; outflow does the reverse). Rules never rewrite existing imports, target accounts must be active, and a rule targeting the bank's own ledger account is skipped. No seed rules.
- Transaction matching: `MatchingEngine` ranks candidates for an imported transaction and never crosses tenants. Deposits suggest open invoices and received customer payments; withdrawals suggest open bills and expenses. Ranking combines exact/close amount, calendar-date proximity, and description signals (record number, party, memo/reference), returns at most 8 with explicit reasons and ranks, and excludes drafts/paid or fully closed records. `GET /bank-transactions/:id/suggestions` is `banking:read`; `POST /bank-transactions/:id/match` is `banking:manage`, row-locks an UNMATCHED transaction, validates direction and an org-owned open target, stores `matchedEntityType`/`matchedEntityId`/`resolutionLabel`/`resolvedAt`, and audits `bank.transaction.match`. Matching is link-only: it posts no journal and leaves invoice/bill/payment/expense records unchanged. A matched or otherwise resolved transaction returns 409 on repeat match or suggestion reads.
- Bank resolution: an UNMATCHED transaction can be resolved once through `POST /bank-transactions/:id/categorize|transfer|expense|payment`. Categorize posts `BANK` lines to the chosen account; transfer moves value between two linked bank accounts; expense creates `EXP-####` and posts to an EXPENSE category from the bank ledger; payment records `PAY-####` against an open invoice and posts the bank deposit against AR. Resolution row-locks the transaction, rejects CATEGORIZED/MATCHED rows with 409, stores `matchedEntityType`/`matchedEntityId`/`resolutionLabel`/`resolvedAt`, and audits `bank.transaction.categorize|transfer|expense|payment`. `banking:manage` only.
- Reconciliation: `ReconciliationSession` is unique per organization/bank account/period and stores the statement ending balance, opening/book ledger balances, cleared total, difference, and ACTIVE/COMPLETED status; clearing lives on `BankTransaction.reconciliationSessionId`/`clearedAt`. `POST /reconciliations` snapshots the ledger opening balance before the period and book balance at period end; `GET /reconciliations`/`GET /reconciliations/:id` resume sessions; `PATCH /reconciliations/:id/transactions/:transactionId` marks or unmarks a transaction cleared. Cleared total is signed in the ledger account's normal direction, cleared balance = opening + cleared total, and difference = statement − cleared balance. Starts and toggles are row-locked, active-only, limited to transactions in the account/period, and audit as `reconciliation.start|clear|unclear`; a transaction already cleared in another session cannot be cleared again. `POST /reconciliations/:id/complete` row-locks an ACTIVE session, recomputes the balances, and only completes when the difference is zero; it stores `completedAt`, `completedById`, and a `completionSnapshot` of the balances. A COMPLETED session rejects clear/unclear/repeat completion with 409. `POST /reconciliations/:id/undo` is COMPLETED-only, restores the snapshot balances, clears the completion fields, and returns the session to ACTIVE. Completion and undo audit as `reconciliation.complete|undo`. Viewer reads, staff/accountant manage.
- Banking: `BankAccount` links one active ledger account (ASSET for checking/savings, LIABILITY for credit cards), unique per organization. `BankingImportEngine` accepts CSV/OFX up to 10 MB, auto-detects headers/delimiters, maps date/description/amount or debit/credit/external-id fields, and normalizes to UTC dates and signed amounts (positive inflow, negative outflow). Duplicate fingerprints use the external ID when mapped, otherwise date+amount+description. `POST /bank-imports/preview` returns headers, mapping, normalized rows, and counts without writing; `POST /bank-imports` skips duplicates and invalid rows, persists a `BankImportBatch` with row/imported/duplicate/invalid counts, and links each row to that batch for undo diagnostics. `GET/POST /bank-accounts`; `GET /bank-transactions` filters by account, date, match state, and search; `GET/POST/PATCH/DELETE /categorization-rules`; `GET /bank-transactions/:id`; `GET /bank-transactions/:id/suggestions`; `POST /bank-transactions/:id/match`; `POST /bank-transactions/:id/categorize|transfer|expense|payment`; `GET/POST /reconciliations`; `GET /reconciliations/:id`; `POST /reconciliations/:id/complete|undo`; `PATCH /reconciliations/:id/transactions/:transactionId`. Transactions start UNMATCHED; rule matches become CATEGORIZED and post `BANK` journals; matching links existing records without posting; direct resolution and created-record links land here. `banking:read|manage` gates the domain; audited as `bank.account.create`, `bank.import`, `bank.rule.create|update|delete`, `bank.transaction.match`, `bank.transaction.categorize|transfer|expense|payment`, and `reconciliation.start|clear|unclear|complete|undo`; no live feed or aggregator.
- Reporting: `ReportingEngine` assembles four read-only statements from tenant-scoped ledger reads. `GET /reports/profit-loss?from=YYYY-MM-DD&to=YYYY-MM-DD`, `/reports/cash-flow`, `/reports/balance-sheet?asOf=YYYY-MM-DD`, and `/reports/trial-balance` all require `reports:read` (every role). Period reports default `to` to today and `from` to the organization's fiscal-year start on or before `to`; as-of reports default to today. Responses echo the effective period, group account rows with `accountId/code/name/amount`, and include totals plus `balanced`, `debitsEqualCredits`, or `reconciled` checks. P&L uses posted ledger balances only. The balance sheet includes a synthetic `Current earnings` equity row (unclosed income minus expense balances through the as-of date) so assets = liabilities + equity without double-counting closed retained earnings. Trial balance shows each account's net balance in the debit or credit column. Cash flow is direct-method: cash accounts are active bank-account ledger accounts plus active Cash `1000`, deduplicated; movements are explained by non-cash counterpart account and classified as operating (income/expense and working capital), investing (fixed/long-term assets), or financing (equity and non-current liabilities). Pure cash transfers are excluded, and beginning cash + net movement must equal ending cash. Ledger math stays in Decimal. Operational analysis sits beside the statements: `GET /reports/sales-by-customer`, `/reports/sales-by-item`, and `/reports/expenses-by-category` take the same period filters/defaults, aggregate only posted documents by invoice issue date/expense date/bill issue date, and exclude DRAFT invoices/bills. Sales use pre-tax invoice-line amounts with tax shown separately; items include quantity. Expenses combine quick expenses and pre-tax bill lines by EXPENSE category and identify each source as `EXP-####` or `BILL-####`. Responses return rows, totals, source arrays, the posted ledger comparison (`ledgerIncome`/`ledgerExpenses`), and a `reconciled` flag. The UI expands rows into source documents and deep-links with `/invoices?invoice=`, `/bills?bill=`, and `/expenses?expense=`. Report export: `GET /reports/:report/export?format=csv|pdf` accepts the same `from`/`to` or `asOf` filters, requires `reports:read`, validates the slug/format/parameter shape, calls the same `ReportsService` methods as the JSON endpoints, and passes the result to `report-export.document.ts` builders plus dedicated CSV and PDF formatters (no duplicated aggregation). Files carry organization identity, report title, effective period/as-of, generated timestamp, grouped rows, totals, and a summary; CSV is RFC 4180 quoted with plain two-decimal amounts, PDF is a ruled Daybook layout with right-aligned amounts and page breaks. Responses are `StreamableFile` attachments named `<report>-<dates>.<ext>` with the matching content type/length. The `/reports` header exposes `Export CSV`/`Export PDF` for the active tab and dates; `/reports` also honors `tab`, `from`, `to`, and `asOf` query parameters so dashboard links land on the right report and period. Dashboard: `GET /dashboard?from=YYYY-MM-DD&to=YYYY-MM-DD` requires `reports:read`, resolves the same effective period as the statements, and returns cash, AR/AP, monthly income/expense trend, recent activity, and derived attention counts. Cash is the active bank-account ledger accounts plus active Cash `1000` deduplicated, with per-account balances through `to` and net change within the period. Receivables/payables reuse `ArAgingService`/`ApAgingService` as of `to` (no second aging implementation). The trend aggregates posted INCOME/EXPENSE journal lines into per-month Decimal buckets that reconcile to P&L. Recent activity merges the latest non-draft invoices, non-draft bills, expenses, customer payments, and bill payments in the period with document/status/amount/href snapshots; attention counts derive from overdue AR/AP and unmatched bank transactions. The owner Overview is fully API-driven (cash table, AR/AP stats, bar trend, recent-activity table, period summary margin) with quick 30/90/365 ranges plus date inputs, deep links into reports/documents/ledger, and usable empty states; no mock Clerk/automation content.
- Attachments: `Attachment` metadata carries `entityType` (EXPENSE/BILL), `entityId`, object key, filename, content type, and size. `AttachmentStore` is the only MinIO caller and owns upload, streamed download, deletion, and 15-minute presigned GET URLs. Uploads are capped at 10 MB and limited to PDF/PNG/JPEG/WebP, validated by extension, declared MIME, and magic bytes, with sanitized filenames. Object keys are `{org}/{entity}/{entityId}/{uuid}/{filename}`; the bucket is created lazily. `GET/POST /attachments`, `GET /attachments/:id/url|download`, `DELETE /attachments/:id`; staff manage, viewer read-only, audited as `attachment.upload`/`attachment.delete`, tenant-scoped, and persisted in the `miniodata` volume.
- Project/time: `Project` has a per-org `PROJ-####` code, optional customer, optional billing item, optional default rate, and active flag. `TimeEntry` records the current member, date, hours, rate, billable flag, optional project, notes, and an optional unique `invoiceLineId`; amount is hours × rate. Invoices and quick expenses carry an optional `projectId`. Time CRUD is `GET/POST /time-entries` and `PATCH/DELETE /time-entries/:id`; a rolled or invoiced entry cannot be edited or deleted, and project-only expense edits stay off the ledger. `POST /time-entries/rollup` row-locks billable, uninvoiced entries from one project, requires a customer and active billing item (from the request or project), creates one DRAFT invoice line per entry with the entry linked through `invoiceLineId`, and posts nothing until the invoice is sent. Invoice line edits are blocked when lines were generated from time, so traceability survives; non-line edits keep the links. Profitability is `GET /projects`, `GET /projects/:id`, and `GET /projects/:id/profitability`: revenue is non-DRAFT tagged invoice subtotals, expenses are tagged quick expenses, and time value reports billable/invoiced/unbilled hours and amounts. Audited as `project.create|update` and `time_entry.create|update|delete|rollup`.
- Agent prompt foundation: `POST /agent/prompts` (`agent:read`, all roles) validates an optional model alias against the server-side `flash`/`flash-lite`/`pro` allowlist, appends a QUEUED `AgentActionLog` row with an `AGT-####` reference, creates an `AgentJob`, and enqueues `agent-prompts`. `GET /agent/jobs/:id` returns status/attempts/model/response/error/log reference plus its logs and proposals; `GET /agent/logs` filters trigger/status/jobId with a capped limit, and `GET /agent/logs/:id`; all tenant-scoped (cross-tenant ids are 404). `POST /agent/test/jobs/:id/advance` exists only when `AGENT_TEST_HOOKS=1` (otherwise 404). `ToolRegistry` owns two read-only tools, `insight.query` (DashboardService snapshot) and `report.generate` (the seven reports plus AR/AP aging), validates args with class-validator (`forbidNonWhitelisted`) and rejects organization/tenant/SQL/code/script keys. The provider is swappable behind `AiProviderService` (`AI_PROVIDER=auto` uses Gemini when `GEMINI_API_KEY` is set, otherwise the deterministic stub; only that service knows Gemini shapes and 429 `RESOURCE_EXHAUSTED`). Jobs retry retryable failures up to `AGENT_MAX_ATTEMPTS` with bounded exponential backoff + jitter, append RETRYING/FAILED log rows, and never hard-fail rate-limited runs. `AgentJob`/`AgentActionLog` statuses are QUEUED/RUNNING/RETRYING/COMPLETED/FAILED; the agent log is append-only with no update/delete routes. Orchestrator: role-filtered tool declarations, at most 3 tool calls/3 rounds, validated execution, then a final answer; write tools are never executed directly (they become proposals), and no DB handle, SQL, or code evaluation is exposed. The `/agent` UI pairs the Ask transcript (composer, aria-live progress, busy/retrying copy, response, visible log reference) with an Activity table and detail.
- Agent write approvals: `ToolRegistry` tools declare `policy: 'auto' | 'approve'`; `invoice.create` is `readOnly: false`, requires `invoices:manage`, and defaults to `approve`. Direct `ToolRegistry.execute` of a write tool throws unless the internal approval token is passed; writes execute only through `ToolRegistry.executeApproved` (called by `ApprovalService` for human approvals or by the orchestrator when an auto policy applies). `AgentProposal` is org-owned with PENDING/EXECUTING/EXECUTED/REJECTED/FAILED, requested/deciding users, JSON args/result, rationale, decision note, timestamps, and log reference; `AgentActionLog` gains optional `proposalId`/`approvalStatus` (still append-only). The orchestrator validates and prepares args (including name → tenant id resolution) and creates one pending proposal per run when the effective policy is approve; read tools and auto-policy writes execute immediately. `GET /agent/approvals` (`status`/`jobId`/`limit`) and `GET /agent/approvals/:id` are `agent:read`; `POST /agent/approvals/:id/approve|reject` are `agent:approve`, granted only to Owner/Admin. Approval re-checks the tool permission, row-locks and requires PENDING, transitions to EXECUTING, executes exactly once under the approver's role/tenant, and stores EXECUTED/FAILED plus decision/execution log rows and audit entries; repeated/concurrent approvals return 409. Rejection row-locks PENDING, stores REJECTED/reason, executes nothing, and logs. Cross-tenant ids are 404; Staff/Accountant/Viewer get 403. The `/agent` workspace adds an Approvals tab (pending count, filter, approve/reject, consequence copy, invoice deep link, no-change copy) and shows approval status/proposal ids in Activity.
- Agent execution policies: `AgentToolPolicy` is org-owned with `toolName`, AUTO/APPROVE mode, optional updater, and unique `(organizationId, toolName)`. `ToolRegistry` marks write/financial tools `sensitive` (currently `invoice.create`) and exposes the full catalog via `listAll`; read-only tools stay fixed auto and non-configurable. `AgentPolicyService.list` returns every tool with default/effective policy, sensitivity, configurable flag, and last update; `resolve` reads the org override at run time (no process cache or worker restart); `update` requires `agent:policy`, rejects unknown (404) and read-only (400) tools, upserts the override, and audits `agent.policy.update` with from/to. The orchestrator routes each call by the effective policy: read-only auto-executes, write + approve creates a proposal, write + auto executes through the internal approved path without a proposal and appends normal tool/result logs; the direct `ToolRegistry.execute` write guard still holds. `GET /agent/policies` and `PATCH /agent/policies/:toolName` (`{policy:'auto'|'approve'}`) are Owner/Admin only; `/agent` adds a Policies tab with the auto-execute warning, per-tool select, Save, updated-by info, and success/error copy. Sensitive tools default to approval until explicitly changed.
- Agent scheduled automations (031): `AgentAutomation` is org-owned with name, mode (CRON or EVENT), five-field `cron`, IANA `timezone` (default UTC), prompt, optional model alias, enabled flag, creator, and last run/status/job/log mirrors; unique `(organizationId, name)`. `cron-parser` validates schedules and computes next runs, and unknown timezones are rejected with `Intl.DateTimeFormat`. `GET/POST/PATCH/DELETE /agent/automations` are `agent:read`/`agent:manage`; create/edit/pause/resume/delete audit as `agent.automation.create|update|pause|resume|delete`. `AgentAutomationScheduler` is the only repeatable-job writer: it registers an `agent-automations` BullMQ scheduler keyed by automation id via `upsertJobScheduler`, so edits replace instead of duplicate; pause/delete remove it and startup re-registers enabled rows. Inline Jest uses the same service with an in-memory map (`AGENT_QUEUE_DRIVER=inline`). `AgentAutomationWorker` consumes due jobs and calls `AgentAutomationRunner`, which loads the row, verifies organization + enabled, re-resolves the creator's membership, enters `TenantContextService.runAs`, creates a CRON `AgentJob` linked by `automationId`, enqueues it on `agent-prompts`, and records `lastRunAt/lastStatus/lastJobId/lastLogReference`; the prompt worker then retries/logs normally and mirrors RUNNING/RETRYING/COMPLETED/FAILED back onto the automation. `POST /agent/test/automations/:id/run` exists only when `AGENT_TEST_HOOKS=1` and returns 409 for a paused automation. `automation.create` is a governed write tool (`agent:manage`, sensitive, default approval) whose handler calls the same automation service, so proposals/auto-policy create one scheduled row and audit it. The `/agent` Automations tab lists schedule/enabled/last run, supports presets + custom cron/timezone, and exposes edit/pause/resume/delete. Cron runs appear in Activity with the CRON trigger.
- Agent event automations (032): `DomainEventsService` is a global in-process bus publishing `{ organizationId, type, entityType, entityId, occurredAt, data }` after the owning transaction commits and is audited; subscriber failures are logged and never fail the business action. Feature services emit `BANK_TRANSACTION_IMPORTED` once per newly imported transaction, `BILL_OPENED` on the first open, `RECONCILIATION_DISCREPANCY` on start/clear/unclear when `difference !== 0`, and `INVOICE_OVERDUE` when a sent invoice is already past due (the deterministic test hook covers the time-passing case). `AgentAutomation` gains nullable `cron`, `eventType AgentDomainEventType?`, and `eventConfig Json?`; unique org+name remains and mode is immutable after create. EVENT configs default to `{ daysOverdue: 0 }`, `{ minAmount: 0 }`, `{ minDifference: 0 }`, or `{}` for bank, validated non-negative (days integer) with unknown keys rejected. `DomainEventRouter` reads enabled EVENT automations for the event organization/type directly, filters with the pure `matchesEventTrigger`, and calls `AgentAutomationRunner.runEvent`, which re-resolves the creator, enters `runAs`, creates a normal EVENT `AgentJob` with an augmented event/record prompt, enqueues on `agent-prompts`, and mirrors last-run fields. `GET/POST/PATCH/DELETE /agent/automations` handle both modes (schedule labels/next-run only for CRON); audit metadata includes mode/eventType/eventConfig. `POST /agent/test/events` (`AGENT_TEST_HOOKS=1`, `agent:manage`, tenant-scoped) publishes `{type, entityId?, data?}` for deterministic tests. `automation.create` accepts mode/eventType/eventConfig through the same approval policy; the stub recognizes event-intent prompts. The UI trigger form supports Schedule vs Event with thresholds and labels.
- Agent slash commands (033): `GET /agent/models` (`agent:read`, every role) returns the server allowlist from `model-catalog.ts` as `{ models: [{ alias, label, modelId, default }], defaultAlias }` without secrets. Prompt submission keeps validating the same aliases (unknown → 400) and stores/uses the selected alias on the `AgentJob`/`AgentActionLog`. The `/agent` Ask composer opens a live `role=listbox` slash menu when the prompt starts with `/` and contains no whitespace, filters `/model`, `/cron`, and `/event` by prefix, supports ArrowUp/ArrowDown (wrapping), Enter, Escape, and click selection with `aria-activedescendant`/`aria-expanded`, and shows "No commands match" plus a clear "Unknown command. Try /model, /cron, or /event." notice that never sends to the model. `/model` opens an allowlisted model selector, updates session-only model state and the composer meta ("Model: Flash Lite"), clears the composer, and sends the alias only on subsequent prompts — it never touches saved automations. `/cron` and `/event` require `agent:manage`, switch to Automations, open the existing new-automation form preset to CRON/EVENT, and focus the name field; nothing is created until the normal form submit through the automation API/`automation.create` policy, and non-managers get a permission message. Commands never bypass ToolRegistry, permissions, tenant scope, or approval policy. The Daybook red-ink composer pulse stops under `prefers-reduced-motion`.
- Demo seed (034): `backend/prisma/seed.ts` is deterministic and idempotent across two organizations, six users, the default chart (now including `1020 Checking account`), customers/vendors/items, mixed-state invoices/bills/estimates, and opening balances. Each org gets one enabled `Weekly cash review` CRON automation (`0 9 * * 1`, UTC) created by its owner; the seed create-if-missing row and best-effort BullMQ scheduler registration (skipped for `AGENT_QUEUE_DRIVER=inline`, Redis failure is a warning). `backend/src/seed.smoke.spec.ts` runs the seed twice, checks no duplicates, signs in all six accounts, and verifies both orgs' distinguishing bank/reconciliation/automation data.

## Gotchas
- Gemini free tier may use prompts/responses to improve Google products; synthetic data only until a billed project is approved.
- `AI-Accounting-User-Flows.html` and `AI-Accounting-Deployment.html` must each be one static file with no build step.
- Production is a free-tier demo: Render web services sleep after idle, Key Value has no persistence, and MinIO has no persistent disk (attachments are ephemeral). Neon free auto-suspends. Demo passwords are published; rotate before real data. The API currently uses the public MinIO HTTPS endpoint because the private Render hostname did not resolve from the container.
- New features stay tenant-scoped, audited, and free of hard-coded industry terms.
- Dates that represent calendar days are `@db.Date`; store/parse them as UTC midnight (`toDate`, ISO `YYYY-MM-DD` slices). Do not let local timezones shift bill/invoice/aging boundaries.
- Money is Prisma `Decimal(14,2)`; never do ledger math in JS floats. Quantities/rates are Decimal and line amounts round to 2 dp.
- Per-org document numbers are allocated by querying the highest existing suffix and retrying unique collisions; preserve that pattern for new document types.
- Migrations must stay chronologically ordered by filename: invoices (11:30) → estimates `20261114113500_estimates` → payments `20261114114014_customer_payments` → vendors/bills `20261114120750_vendors_bills` → bill payments `20261115164901_bill_payments` → expenses `20261115222500_expenses` → attachments `20261115233000_attachments` → banking `20261116001000_banking` → categorization rules `20261116011500_categorization_rules` → bank transaction resolution `20261116014500_bank_transaction_resolution` → reconciliation sessions `20261116030000_reconciliation_sessions` → reconciliation completion `20261116060000_reconciliation_completion` → projects/time `20261116100000_projects_time` → agent foundation `20261116103911_agent_foundation` → agent approvals `20261116113000_agent_approvals` → agent policies `20261116122719_agent_policies` → scheduled automations `20261116130000_scheduled_automations` → event automations `20261116140000_event_automations`. Renaming a migration requires a matching remote delete when pushing, and fresh shadow-DB `migrate deploy` must still succeed.
- MinIO: the backend container reaches `minio:9000`, while presigned URLs use `MINIO_PUBLIC_ENDPOINT=localhost:9000` so the browser can fetch them. The bucket is auto-created on first upload. Jest uses the in-memory `AttachmentStore` (`ATTACHMENT_DRIVER=memory`); Playwright uses real MinIO, so `minio` must be running and files persist in `miniodata`.
- Reports default period ends today and starts at the organization's fiscal-year start on or before that date; as-of reports default to today. Operational reports share that period resolution, use invoice `issueDate`/expense `date`/bill `issueDate` boundaries, exclude DRAFT invoices and bills, keep tax out of sales/expense totals, and aggregate in Decimal. Cash flow treats every cash account movement as debit−credit (so bank-import signs hold), classifies non-cash counterparts by account type/subtype, and skips entries with no non-cash counterpart so transfers never masquerade as income.
- Dashboard balances are as of the period end (`to`), while the trend and recent activity are bounded by `from`/`to`; cash net change includes opening entries inside the period. Attention counts are derived (overdue AR/AP via aging services, unmatched bank transactions) and the UI shows `All clear` when they are zero. `/reports` reads its initial tab/dates from the URL once on mount.
- Projects/time: roll-up only accepts billable, uninvoiced entries from one project and requires an active customer and billing item. One invoice line is created per time entry so `TimeEntry.invoiceLineId` stays unique; the invoice is DRAFT and posts nothing. Editing lines on a time-built invoice is rejected, while notes/date/project edits preserve the links. The project/new-project navigation lives in both the shared `AppSpine` and the Overview's inline spine.
- Bank imports are signed cash movement: positive is money in, negative is money out. Rule priority is ascending (0–1000; lower first), ties break by `createdAt` then id; imports post `BANK` journals with `sourceId` = transaction id, so duplicate imports cannot double-post. Rule edits/deletes never recategorize existing transactions. Resolution and matching are one-way: row-locked UNMATCHED only, with linked entity/label snapshots; the UI hides Resolve after state changes. Matching links an existing invoice/bill/payment/expense and posts nothing, while resolution creates or points at a ledger account. Deposits only match open invoices or received payments; withdrawals only match open bills or expenses. Reconciliation sessions are one per account/period; clearing is book-direction aware, recalculates cleared total/balance/difference immediately, and cannot double-clear a transaction in another session. Completion requires a zero difference and locks the session; undo is the only way back to ACTIVE and restores the completion snapshot. CSV mapping is required when headers are ambiguous; OFX fields are standard. Dates normalize to UTC midnight. Never move CSV/OFX parsing into the frontend.
- Agent queues: `AGENT_QUEUE_DRIVER=bull` (Compose, Redis `agent-prompts`) or `inline` (Jest, set in `env.setup.ts`). Both share `AgentRunnerService`; the worker re-resolves membership from `userId`/`organizationId` before `TenantContextService.runAs`, so never call scoped services before that. Retryable 429s become RETRYING with bounded backoff+jitter; the final attempt appends FAILED. `POST /agent/test/jobs/:id/advance` is 404 unless `AGENT_TEST_HOOKS=1`. `AgentActionLog`/`AgentJob` rows are append-only at the API; E2E cleanup deletes only its own prompt's rows directly in Postgres (the agent spec does this in `afterAll`).
- Agent model aliases resolve server-side (`AGENT_MODEL_FLASH|FLASH_LITE|PRO`, default `AGENT_DEFAULT_MODEL=flash`); unknown aliases are 400 before a job is created. `AI_PROVIDER=auto` picks Gemini only when `GEMINI_API_KEY` exists, otherwise the deterministic stub (no network); only `AiProviderService`/`GeminiProvider` know provider shapes. Tool args are validated with class-validator and any organization/tenant/SQL/code/script key is rejected (the sensitive-key check is exact-key, so `itemCode`/`customerName` are fine); tools only call tenant-scoped read services.
- Agent approvals and policies: the orchestrator resolves the effective policy per tool call. A write with `approve` becomes a PENDING `AgentProposal`; a write with `auto` executes immediately through `ToolRegistry.executeApproved` with normal tool/result logs and no proposal. The internal approval token still blocks direct `ToolRegistry.execute`; `ApprovalService` also uses the approved path for human-approved proposals. Approval marks EXECUTING in a row-locked transaction before executing, so concurrent/repeat approvals get 409 and produce one invoice; execution failure stores FAILED plus a log/audit row, never a partial retry. Names resolve to exactly one active tenant customer/item at proposal time (missing/ambiguous → 400, no proposal). Rejection stores REJECTED and never touches the ledger. The stub proposes `invoice.create` for create-invoice prompts using seeded names and `due in N days`; write proposals are capped at one per run. E2E cleanup deletes its own proposal/log/job/invoice/policy rows via SQL, including `AuditLogEntry` rows.
- Agent policies are read from `AgentToolPolicy` at run time, so saving a policy applies to the next run without a worker restart. Read-only tools are fixed auto and non-configurable; write tools are sensitive and default approve until an Owner/Admin changes them. `PATCH /agent/policies/:toolName` returns 404 for unknown tools, 400 for read-only tools or invalid modes, and audits `agent.policy.update` with from/to. Never cache effective policies in process memory.
- Domain events and event automations: publish only after the owning transaction commits and audit rows are written (never inside a tx). Handlers are in-process and errors are swallowed, so automation routing cannot break the business action. `DomainEventRouter` is system routing, reads candidate rows directly but always filters by the event's `organizationId`, and only enabled EVENT rows with a matching `eventType` and threshold fire. `AgentAutomation.cron` is nullable; only CRON rows register BullMQ schedulers, and mode cannot change after create. Thresholds are `daysOverdue` (invoice, integer), `minAmount` (bill), and `minDifference` (reconciliation absolute); bank events have no threshold. The event test hook is `POST /agent/test/events`, 404 unless `AGENT_TEST_HOOKS=1`. Event runs use the normal EVENT `AgentJob`/prompt-queue/tool/approval path, and the prompt carries the record context. `invoice.send` only emits when the invoice is already overdue at send time; use the hook to simulate time passing.
- Agent slash commands are composer UI only: `/model` keeps the alias in component state and passes it to `POST /agent/prompts` on later runs; it must not alter `AgentAutomation.model`. `/cron`/`/event` only open the existing automation form and are gated by `agent:manage`; they never create or run automations directly. The menu opens only for a leading `/` with no whitespace; exact commands with a trailing space still route, unknown commands show the help notice and are never sent.
- Agent automations: the scheduler is the only repeatable-job writer and is keyed by automation id, so edits must call `upsertJobScheduler` (never `queue.add` with a repeat option) and pause/delete must remove the scheduler. Keep the scheduler free of runner/tool dependencies — the worker consumes due jobs and the runner re-resolves the creator’s membership before `runAs`; a DI cycle with `ToolRegistry` will break startup otherwise. Cron is five fields plus an IANA timezone (`cron-parser` + `Intl`); invalid values are 400. The test hook (`POST /agent/test/automations/:id/run`) is 404 unless `AGENT_TEST_HOOKS=1` and 409 for paused rows; Compose needs that env exported for Playwright. Runs are normal `AgentJob` rows with trigger CRON and `automationId`, so retries/logs/approvals all share the prompt worker; completion mirrors status back onto `AgentAutomation`. Presets are UI sugar only — the API always stores the cron expression.
- The Overview has its own inline spine nav (`frontend/app/page.tsx`) in addition to shared `AppSpine`; add new nav items to both or Overview users lose the link.
- Playwright label/heading selectors are ambiguous across drawers and tables; use `{ exact: true }`, `{ level: 1 }`, or scope to a region. `Payments` also matches `Bill payments`. Wait for drawers to finish animating before screenshots; close them with `Escape`.
- The Vercel project was created API-first and its Git auto-deploy setting is disabled. After frontend changes, create a production deployment from the current `main` commit (or redeploy the latest from the dashboard). Backend changes still auto-deploy from `backend/**` on Render.
